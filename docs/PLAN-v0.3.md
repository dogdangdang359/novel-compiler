## 范围与任务

### Phase 0 —— 解析器兼容（前置，必做）

**P0.1 章节标题解析放宽**（`src/extract.js`）
- 接受（保持行号锚点不变）：
  - Markdown 标题：`# 第1章 铜钟`（现状，不回退）
  - 纯文本标题：`第1章 夜雨孤灯`、`第 1 章 …`、`第一章 …`（中文数字）
  - 特例章节：`楔子` / `序章`（= 第 0 章）、`尾声` / `番外` / `后记`（不参与编号）
- 解析失败兜底：无任何章节标题时，错误信息提示"支持 `# 第N章` 或 `第N章` 两种格式"
- 交付物：HEADING_RE 扩展 + 错误提示改进

**P0.2 真实回归夹具**（`test/fixtures/`）
- 从 `exam.md` 提取有代表性的片段（含纯文本标题、中文数字标题、楔子类标题）做夹具；避免整文件（大而脆）
- 交付物：`plain-heading-manuscript.md` + 配套 `plain-heading-canon.json` + 测试场景

**验收**：exam.md 能正确分章并产出 problems；现有 65 项测试零回归；新增 2-4 项断言。

### Phase 1 —— 增量提取（README 路线图 "增量提取"）

**P1.1 范围提取**（`extract-llm.js` + `src/extraction.js`）
- 新增 `--from <章号>` / `--to <章号>`：只提取指定章节范围（提示词只携带该范围的行号文本）
- 基线语义不变：既有 canon 全部条目保留；范围外章节的条目**只保留、不修正**

**P1.2 合并语义**（`src/extraction.js` 新增 `mergeProposal`）
- 范围提取输出 = 完整 canon（基线 + 范围内修正/新增），合并规则：
  - 范围内证据命中的条目 → 用提议值覆盖字段
  - 范围外条目 → 原样保留基线值
  - 新增条目必须带范围内证据（反幻觉校验复用）
- 用测试锁住语义：修改第 N 章 → 只有第 N 章相关条目字段变化

**P1.3 IDE 联动**（`app/public/app.js` + `app/server.js`）
- 顶栏/AI 面板增加"增量提取"入口：`--from <光标所在章>` 或"提取本章"
- 保存后提示是否增量提取（不自动跑，避免意外成本）

**验收**：新增一章的提取成本 ≈ 单章 token；范围提取测试覆盖"改第 3 章不动第 1/2 章条目"。

### Phase 2.1 —— IDE diff 审阅（README 路线图 "IDE 增强：diff 视图"）

**P2.1.1 后端 diff 接口**（`app/server.js`）
- `POST /api/diff-canon { baseline, proposal }`：复用 `src/diff.js` 的字段级 diff 思路，输出结构化 `{added, modified, unchanged}`（比 diffCanons 更偏"审阅"而非"漂移"，新写轻量函数）

**P2.1.2 前端审阅视图**（`app/public/app.js` + `index.html` + `style.css`）
- 提取完成后弹出/切到审阅面板：按 实体/知识/悬念/时间线 分组
  - 新增条目：绿色高亮，证据引文展示（行号+原文），按钮 `接受` / `拒绝`
  - 修改条目：黄色高亮，旧值→新值 对照，按钮 `接受` / `拒绝` / `编辑后接受`
  - 接受 → 写回实际 canon（`/api/save` 原子写）并自动 `compile` 刷新 problems
- 这是"AI 提议、人确认"治理的最终 UI 形态

**验收**：提取 → 审阅（接受/拒绝/编辑）→ 合并 → 编译刷新，全流程不出 IDE；拒绝的条目不进 canon。

## 风险与对策

| 风险 | 对策 |
|---|---|
| 真实章节格式比预想更多样（如 `第 1 章` 带空格、`第1章`无空格） | P0 用正则覆盖常见变体 + 解析失败友好提示兜底 |
| 范围提取的合并语义出 bug（改 A 章误动 B 章条目） | P1.2 合并函数纯函数化 + 专项测试锁行为 |
| diff 审阅误写回（拒绝的条目进 canon） | 审阅操作只通过后端原子写 + 每次合并后自动 compile 可见性验证 |
| exam.md 夹具过大/过脆 | 夹具用代表性片段，不整文件引用 |
